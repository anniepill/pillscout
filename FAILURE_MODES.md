# What the model did, and what we changed

Notes from testing the first PillScout MCP server against Claude and Gemini, April to May 2026. Each line is a real exchange: what the model did with what the server returned, and the change we made so it could not happen the same way again. The pattern across all of them is the lesson: when the model drifted, another paragraph of instructions held for a while; a change to the shape of the data held.

| What we saw | What it taught | What we changed |
|---|---|---|
| A multivitamin whose brand name contains "Twice Daily" was saved as taken twice a day. The label says once. Every total after that was doubled. | The model will read a name as an instruction, and a guess saved into a field looks exactly like a fact. | Every frequency carries its source: user stated, manufacturer default, or inferred. |
| The server returned 120 mcg of vitamin K. The model said 500 to 600, then invented a per-capsule split and a capsule count and reported 2,400 mcg, with warfarin advice on top. | Once one number is invented, everything built on it sounds just as confident. | Return `per_capsule_breakdown: null` as a visible field. The model does not divide what the response says cannot be divided. |
| A search for one product returned a different product with a similar word in its name. The response was well formed, so nothing questioned it, and it was cached for thirty days. | A valid shape is not a right answer. | A similarity gate before any match is accepted, and a `matched_product_name` field so the reader can see what was matched. |
| A product came back with every ingredient list empty. Downstream code treated "found" as "covered" and missed its vitamin K. | An empty list is read as "nothing there," not "we don't know." | Coverage became an explicit state: `not_in_database`, `evaluated_not_flagged`. Absence is a field, never an empty array. |
| In a fresh chat with an empty cabinet, the model answered against seven items it remembered from an earlier conversation. | The model's memory sits above the server; no server instruction can reach it. | A freshness token in every cabinet response that the model must echo, binding its answer to a specific retrieval. |
| A quick name-level scan found nothing and the model said "no major interactions." A full scan of the same items flagged two upper-limit exceedances. | The model will narrate thin data as complete if nothing says how deep the check went. | An `analysis_depth` field the model must surface. |
| A class-level check ("anticholinergic burden reviewed") was narrated as if each substance had been checked by name. | One response shape carrying two meanings is read as the stronger one. | A `coverage_basis` field so each engine declares its own scope. |
| A wrong match was announced as "a surprise find a pregnant woman would never know without PillScout." | Praise around a number makes it harder to question. | Stop the bad match at the resolver, before there is anything to praise. |
| The model overruled a correct upper-limit flag with its own pharmacology (topical versus oral magnesium). It happened to be right. | An unsourced override is a drift even when it is correct, because it will be just as confident when wrong. | Route of administration in the engine, so there is nothing to override. |
| Asked to write a prompt for my coding tool, the model put invented clinical facts in the prompt itself. | Fabrication can happen before any tool is called; no schema reaches it. | A source check on every prompt before it runs. A process rule, not code. |

The field names in the third column are from the first server and from the rebuilt server's specification, both private; none of them is in this repository.

What did not break, across three reviews of the transcripts: the model did not reword a verbatim quote, did not invent a citation in its answer, did not strip a disclaimer, and did not ignore a hard refusal. Likely because the early server rarely returned those shapes. The corpus that followed carried them, and they were tested on purpose.

The rule that came out of this and governed everything after: every value carries its source, every absence is a field with a reason, every check says how deep it went, and bad data is stopped at the boundary before a model can narrate it. The corpus states, with the source. The model reasons. What sits between them is a schema, not a paragraph.
